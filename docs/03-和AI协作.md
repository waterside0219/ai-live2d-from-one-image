# 和 AI 协作：派活、交接、验收

整个项目由三方完成：一个 agent 负责施工，另一个 agent 负责写施工单和验收，人负责提供原画、做决定、在真机上试。这一篇讲这套配合怎么运转。具体怎么做见[教程](01-教程.md)，我们在协作上踩过的坑见[踩坑复盘](02-踩坑复盘.md)。

## 分工随阶段和授权变化

| 阶段 | 阿年 | Astra（GPT 6 Astra，Codex 桌面版） | 沈砚（Claude Opus 5.5） |
|---|---|---|---|
| V1 | 指定由 Astra 来做 | 施工 | 没参与（施工单由另一位 AI 助手写，也由它验收） |
| V2 | 后半程直接带着 Astra 改，最后确认 | 施工 | 写细调单和参考资料整理 |
| 接入手机 | 授权 | **获得授权后实际装机**，并通过 USB 逐个读回 16 个文件，SHA 全部一致 | 写接入单 |
| 重做模型 | 看图拍板，中途纠正方向 | 施工；**单子里明确禁止自己往手机发送** | 写施工单和返修单，验收，装机 |
| 桌宠 | 在 Windows 上试用 | 调研，第 2–6 步施工（只用 mock） | 选方案，部署服务器和隧道，打开真实接口，在 Windows 现场排错 |

谁能碰设备、碰服务器、碰钥匙，每张施工单都要写清楚。不能默认为“一直是谁”。

## 写施工单

### 哪些写死，哪些写依据

我们一开始总结的是“第一条把做法写死”。可是**返工最大的一轮，恰恰就是因为把一个没验证过的方法写死了**：当时规定“全部 AI 重画，禁止抠像素”，结果变了脸（见[复盘坑2](02-踩坑复盘.md#坑2-定稿立绘逐件-ai-重画变了脸)）。所以我们把原则改成了下面这样：

- **必须写死的**：
  - 目标；
  - 保护对象：哪些像素、文件、行为不能动；
  - 授权范围：能改哪些文件，能不能碰设备、服务器、钥匙；
  - 验收标准：硬数字，以及要看哪些画面。
- **方法要写，但要附上依据，并写清失败了怎么办**：例如“可见部分用原图像素，因为逐件重画会变脸（有 r04 为证）；如果这样做不通，就停下来写清原因，给出两个方案交给验收方选，不要自己暗中换路线”。**没验证过的方法，不要写成铁律。**
- **措辞要防止被按字面误读**：比如“不许变”，要写明是“验收时看像不像”，还是“不许动这些像素”。
- **区分两种“停”**：
  - 组内自检没过：自己接着修，不要停下来等人确认。
  - 阶段验收没过：下游不能开工。
  - 例外是调研类任务：写完结论就停下，等对方选方案。我们做桌宠的第 1 步就是这样。
- 写完后，对照参考原文逐句再核一遍。

### 施工单骨架

```markdown
# <项目> 开工单 <版本> · <日期时间>

## 〇、边界（先读）
- 基线：以 <冻结目录/版本号> 为底；旧版本一律不许覆盖。
- 只许改：<文件/图层/参数，逐个列出>
- 保护：<默认态可见像素 / 已经通过的部件 / 已有手势和接口>
- 禁止：<碰设备、服务器、钥匙 / 自己往设备送>
- 方法：<做法>，依据：<证据>；做不通就停下，写出两个选项问 <验收方>，不要暗中换路线。
- 先读：<文档清单，精确到章节>

## 一、要做什么（逐条：现状 → 要改成什么 → 为什么，引用用户原话或真机反馈）

## 二、交付自查（自己先查，过不了不许交）
- 硬数字：默认态和原图 native/2x RGBA 最大差 0；GPU 不透明区域 RGB 差 0（附上数字）
- 画面：手机大小的整图 + 400% 局部，都和原图并排；列出必须截的帧
- 视频：40 秒，包含 <待机 / 眨眼 / 戳左脸 / 戳右脸 / 狂戳 3 秒 / 摸两只耳朵 / 说话>
- 测试：现有测试照常跑；原本就失败的单独列出，不许放宽断言
- 版本号 <...-rN>，输出到新目录；回滚基线 <rM>
- README 逐条对应第一节的每一条

## 三、不做 / 留给谁
```

开工单本身写进文件，开工时给 agent 的话只要一两句，例如：“读某某施工单，先做第 1 步调研，写完停下等验收方，不要开始第 2 步。”

## 交接规矩

- 下一步只能用上一步已经冻结的文件，并附上 SHA 清单。上一步没通过验收，下一步不能开工。
- 哪一步出了问题，就退回哪个窗口去改。**下游不许顺手改上游**，比如建模时发现耳根没画够，要退回拆图那一步补画，不能把网格拉长去遮。
- 每个窗口只写自己的目录，以及交接文档里属于自己的那一段。
- agent 的上下文会被写满，所以要让它写断点文件，新窗口从断点接着做。

## 验收规矩

1. **先列逐条对照表**：参考资料里的每一条，都和交付物一一对上。没对完就不说“好了”，只说“还差哪几条”。
2. **自己核对，不要直接相信对方报的数字。** 比如自己把参考图按最近邻放大 2 倍，再和拼合图做差。
3. **先按手机实际大小看，再放大到 400% 看**，而且始终和原图并排。
4. **动态要拆帧看**，并且用运行端真实会出现的参数组合（具体方法见[教程第 4 步](01-教程.md#4-本机预览与验收方法)）。
5. **证据要和哈希绑定**：报告里写明实际加载的 MOC、纹理、动作、物理文件的 SHA。
6. **分清验到了哪一层**：能加载、能动、好看，是三个不同的层级。本机通过不等于手机通过，网页通过也不等于 VTS 通过。
7. **没全部测过，就不说“好了”**。把已验和未验的项目都列出来。
8. 交付说明里，不要声称对方已经读过、已经确认或已经装好。
9. 找问题是验收方的工作，不要等用户自己用出问题。
